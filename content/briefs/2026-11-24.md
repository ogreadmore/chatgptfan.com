AI is making familiar security mistakes easier to exploit. That is the practical warning in the UK National Cyber Security Centre’s [November 24 assessment](https://www.ncsc.gov.uk/blogs/familiar-weaknesses-exploited-faster-defending-against-agentic-cyber-attacks): attackers are using agents to search, try an approach, read the result and keep going at low cost.

The agency reports increased AI-assisted attacks since September, including service disruption and compromised systems. Its examples include exposed credentials, missing authentication and misconfigured services. This describes incidents the NCSC has observed; it is not a measurement of every attack worldwide or proof that an AI agent can defeat any defense.

### Start with access, not another promise

For people building with AI, the distinction between a working demo and a safely deployed service matters. Ask what a stranger can reach, which credentials the application possesses, and what those credentials permit. A convincing demonstration does not answer those questions.

The NCSC’s [API guidance](https://www.ncsc.gov.uk/collection/securing-http-based-apis/2-api-authentication-and-authorisation) separates identifying a caller from deciding what that caller may do. It recommends denying access by default, limiting permissions and checking them for each request. A successful login should not become unrestricted access to everyone’s data.

Its [repository guidance](https://www.ncsc.gov.uk/collection/developers-collection/principles/protect-your-code-repository) also recommends keeping secrets separate from source code, scanning for exposed keys, promptly removing access that is no longer needed, and reviewing code changes. These are concrete checks for an AI-assisted project before it becomes someone else’s dependency.

### New defensive tools still need testing

There is a relevant development on the defender’s side. On November 23, [OpenAI and Cisco introduced Shirudo](https://openai.com/index/introducing-shirudo/), an open-source Linux runtime for temporary protections while teams prepare patches. Operators test and approve those protections; OpenAI describes a controlled demonstration, not universal protection for production systems.

A useful defensive tool can buy time. It does not remove the need to control access or complete the permanent repair.

For everyday users, the NCSC’s [personal security guidance](https://www.ncsc.gov.uk/collection/top-tips-for-staying-secure-online) offers a simpler starting point: protect email with a separate password, enable two-step verification, install updates and back up important files.

Our view: stronger defensive tools are welcome, but the growing burden on defenders also belongs in decisions about releasing more capable systems. Readers should not have to accept faster attacks as an unavoidable price of useful AI.
